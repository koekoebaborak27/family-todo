# スキル: CI をスキップして push する

CI（GitHub Actions）を起動させずに変更を push する。**対象はドキュメントに限らず、ソースコードの修正でも使える。**

このファイルが手順の**正本**。Claude Code / GitHub Copilot / Codex の各入口ファイルは、ここを読ませるだけの薄いラッパーであり、手順を複製しない。

仕組みそのものの解説（`paths-ignore` と `[skip ci]` の違い、注意点）は [`README.md`](../../README.md) の「ドキュメントだけの変更でCIを実行しない（`main`へ直接push）」にある。**説明が食い違ったら README を正とし、この手順書を直す。**

## このスキルの中核

CI をスキップすると、[`ci.yml`](../../.github/workflows/ci.yml) の全ステップ（lint / format:check / typecheck / test。プロジェクトで足したビルドやマイグレーション適用も含む）が**1 つも実行されない**。ソースコードに対して使えば、壊れたコードがそのまま `main` に載る。

そのため、このスキルは**実行前に必ずユーザーの明示的な承認を取る**（手順 4）。承認を得るまでコミットも push もしない。

## 使うタイミング

- 「CI スキップでプッシュして」「CI なしで push して」と指示されたとき
- CI の待ち時間を省きたい / Actions の使用時間を節約したいとき
- CI が外部要因（GitHub 側の障害、依存パッケージの一時的な不具合）で通らず、先に変更を反映したいとき

対象ファイルによる制限はない。ただし**何を失うかは対象によって大きく違う**ので、手順 2 で必ず区別する。

## 手順

### 1. 変更内容を把握する

```powershell
git status --short
```

```powershell
git diff --stat
```

```powershell
git branch --show-current
```

ステージ済み・未ステージの両方を確認する。意図しないファイル（`.env`・ビルド生成物・`node_modules/`）が混ざっていないかもここで見る。

### 2. リスク区分とスキップ方式を判定する

| 変更内容 | リスク | スキップ方式 |
|---|---|---|
| `*.md` と `docs/**` **だけ** | **低**。CI の検証対象外のファイルなので、失うものがない | `paths-ignore` が自動でスキップ。**`[skip ci]` は付けない** |
| `.claude/**` / `.agents/**` のうち `*.md` 以外（`settings.json` など） | **低**。アプリのビルドに含まれない | `[skip ci]` |
| `src/**` / `package.json` / `*.ts` / `*.json` などコードを含む | **高**。lint・型チェック・テスト・ビルドがすべて未検証になる | `[skip ci]` |
| `.github/workflows/**` | **最高**。CI 設定が壊れていても気づけず、以降 CI が動かなくなる可能性がある | `[skip ci]` |

低リスクの場面で `[skip ci]` を不要に付けない。付けると `paths-ignore` が働いたのか区別できなくなり、設定が壊れても気づけない。

### 3. 高リスクの場合はローカル検証を提案する

コードを含む変更（リスク「高」「最高」）では、**CI の代わりにローカルで同じ検証を通すことを提案する**。ユーザーが不要と言えば飛ばしてよいが、提案自体は必ず行う。

```powershell
pnpm lint; pnpm format:check; pnpm typecheck; pnpm test
```

プロジェクトで `pnpm build` を追加している場合はそれも実行する。DB マイグレーションの適用検証（0 からスキーマを再現できることの確認）を CI に入れている場合、ローカルの適用済み DB では検証にならないため代替できない。**マイグレーションを追加した変更で CI をスキップすると、この検証だけは他に手段がない**ことを伝える。

### 4. ユーザーに確認する（必須ゲート）

**ここで必ず止まる。** 次を提示し、明示的な承認を得るまでコミットも push もしない。「たぶん大丈夫」で進めない。

提示する内容:

| 項目 | 具体例 |
|---|---|
| 対象ファイル | `git status --short` の結果をそのまま |
| push 先ブランチ | `main` へ直接か、feature ブランチか |
| スキップ方式 | `paths-ignore`（自動）か `[skip ci]`（手動）か |
| リスク区分 | 手順 2 の表のどれに当たるか |
| **実行されなくなる検証** | リスク「高」以上では 8 ステップを具体的に列挙する |
| ローカル検証の結果 | 手順 3 を実行した場合はその結果。していない場合は「未実施」と明記 |
| 取り消し方法 | push 済みなら `git revert`。`main` 直接 push では PR のような見直しの機会がないこと |

確認の取り方:

- **リスク「低」**: 対象ファイルと方式を示し、「この内容で push してよいか」を確認する
- **リスク「高」「最高」**: 上記に加えて、**未検証のまま `main` に載ることを明示**し、「通常は feature ブランチ → PR → CI green が推奨。それでも CI をスキップするか」を問う。ユーザーが再度スキップを選んだ場合はその判断に従い、以降は反対意見を繰り返さない

### 5. コミットメッセージを組み立てる

[`REVIEW.md`](../../REVIEW.md) に従い、**何を・なぜ・どう検証したか**を書く。加えて、`[skip ci]` を使う場合は次の 2 点を本文に必ず残す。

- **なぜ CI をスキップしてよいと判断したか**（対象がドキュメントのみ／ローカルで CI 相当を実行済み／CI 側の障害を回避、など）
- **代わりに何を検証したか**（手順 3 の結果。未実施なら「ローカル検証も未実施」と正直に書く）

`[skip ci]` は**件名の末尾**に置く。使える文字列は `[skip ci]` / `[ci skip]` / `[no ci]` / `[skip actions]` / `[actions skip]` の 5 つで、効果は同じ。

### 6. コマンドを提示する、または実行する

git 操作を代行するか手順提示に留めるかは、**その都度の指示に従う**。提示する場合は **1 コマンドにつき 1 つのコードブロック**に分け、各コマンドの後に「何が表示されれば正常か」を書く。

```powershell
git add <対象ファイル>
```

```powershell
git status --short
```

```powershell
git commit -m @'
<件名> [skip ci]

## 何を / ## なぜ / ## どう検証したか
'@
```

```powershell
git push
```

PowerShell のヒアストリングは**閉じる `'@` を行頭**に置く（インデントすると構文エラー）。

### 7. CI が起動していないことを検証する

```powershell
gh run list --limit 3
```

**今回のコミットに対応する行が現れなければ成功。** スキップされた場合は「失敗」ではなく run 自体が作られないため、`Actions` タブにも履歴が残らない。

行が現れてしまった場合の切り分け:

| 原因 | 確認方法 |
|---|---|
| `[skip ci]` の綴り違い・角かっこ抜け | `git log -1 --format=%s` |
| `paths-ignore` を期待したがコードが混ざっていた | `git show --stat HEAD` |
| `paths-ignore` のパターン不一致 | [`ci.yml`](../../.github/workflows/ci.yml) の `on:` を確認 |

### 8. 報告し、必要なら後始末を案内する

- 実行を代行した場合は、実行したコマンドをそのまま提示する
- どちらの方式でスキップしたかを明示し、手順 7 の結果を根拠として示す
- **リスク「高」以上でスキップした場合は、未検証が残っていることを報告に明記する。** 次にコードを変更して CI が走るとき、今回の分もまとめて検証される。そこで初めて失敗が出る可能性があることを伝える

## 注意点

- **`main` へ直接コミットする場合、Pull Request のような見直しの機会がない。** 取り消すには `git revert` が必要
- **`paths-ignore` が効くのは GitHub Actions だけ。** 本番デプロイの Cloud Build は別の仕組みで、ドキュメントのみの変更でもデプロイが走る。止めるならコミットメッセージに `[skip ci]` を付ける（Cloud Build も同じ文字列に対応）。**コードの変更を `[skip ci]` で push すると、CI もデプロイも両方止まる**点に注意する
- **`.github/workflows/**` を `[skip ci]` で push するのは特にリスクが高い。** YAML の構文エラーがあると以降 CI が起動しなくなる。最低限 `pnpm exec prettier --check <対象>` でパースが通ることを確認する
- `main` にブランチ保護はかかっていないため直接 push できるが、それは「やってよい」という意味ではない。**このスキルが省略してよいのは CI の実行だけで、手順 4 の確認は省略できない**
