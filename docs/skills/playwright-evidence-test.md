# スキル: Playwrightで画面操作テストを実行しエビデンスを残す

Markdown形式の単体テスト仕様書・テスト対象URL・ログイン情報・DB接続情報を受け取り、Playwrightで画面操作を自動実行する。必要ならDBの事前データを整え、操作後にDBの状態を確認し、PNGスクリーンショットとDB状態（CSVまたはJSON）、実行結果Markdownを `docs/test/unit/result/<ドメイン>/` 配下のテスト単位フォルダにエビデンスとして保存する。

このファイルが手順の**正本**。Claude Code / GitHub Copilot / Codex の各入口ファイルは、ここを読ませるだけの薄いラッパーであり、手順を複製しない。

[`TESTING.md`](../../TESTING.md) は単体テスト（Vitest）のみを扱い、「E2E（Playwright）は別途定義する」としている。**このスキルがその E2E 部分にあたる。** 雛形は [`playwright.config.ts`](../../playwright.config.ts)（`testDir: ./e2e`）としてすでに置かれているが、`@playwright/test` 本体は未導入（`package.json` の `devDependencies` に無い）。

テスト仕様書がまだ無い場合は、先に [`create-unit-test-spec`](create-unit-test-spec.md) スキルで作成する。

## このスキルの中核（何が危険か）

| リスク | 内容 | 対策 |
|---|---|---|
| パスワードの漏えい | チャット本文やコミット履歴にパスワード平文が残る | 環境変数を優先し、値そのものをチャットや生成物に書かない（手順2） |
| 本番DBの破壊・情報漏えい | 誤って本番DBに接続し、書き込み・全件取得してしまう | 接続先を必ず判定し、ローカル/検証用以外では停止する（手順3） |
| 本番画面への誤操作 | 本番 URL に対して登録・削除等の操作を自動実行してしまう | 対象URLを判定し、本番らしき文字列では停止する（手順3） |
| 意図しないファイル生成 | テストコード・エビデンスが無承認で大量に作られる | 実行前に保存先と内容を提示し、承認を得てから作る（手順3） |

## 使うタイミング

- 「Playwrightで画面操作テストして」と依頼されたとき
- Markdownの単体テスト仕様書に沿ってブラウザ操作をしたいとき
- ログイン、入力、登録、検索、編集、削除などの画面操作を自動化したいとき
- DBの値を事前に準備し、画面操作後のDB状態を確認したいとき
- `docs/test/unit/result/<ドメイン>/` 配下にPNGスクリーンショット、DB出力CSV/JSON、実行結果Markdownを保存したいとき

## 受け取る情報（事前確認）

| 項目 | 必須 | 備考 |
|---|---|---|
| テスト仕様書のパス | ○ | Markdown形式。例: `docs/test/unit/spec/<ドメイン>/UT_10_一覧検索.md`（`create-unit-test-spec` スキルの保存先規則） |
| テスト対象URL | ○ | 例: `http://localhost:3000`。既定は `playwright.config.ts` の `E2E_BASE_URL` |
| ログインID | ○ | 画面操作でログインが必要な場合 |
| パスワード or 環境変数名 | ○ | **環境変数名を優先して聞く**（手順2）。`.env.example` に自動テスト用アカウント（`SEED_ADMIN_PASSWORD` 等）が用意されている場合はそれを使ってよいか確認する |
| エビデンス保存先フォルダ | — | 聞かない。`docs/test/unit/result/<ドメイン>/テスト結果<仕様書のファイル名（拡張子を除く）>/` に固定する（「エビデンス保存の命名規則」参照） |
| DB確認対象（テーブル名） | 画面操作がDBを変える場合は○ | 例: `contracts, contract_parties, contract_terms` |
| DB接続情報 | DBを確認・準備する場合は○ | 通常は `DATABASE_URL` 環境変数（値そのものは読まない。手順3） |

**不足があれば必ずユーザーに質問する。憶測で仕様書やURLを補わない。**

## 手順

### 1. 仕様書からテストケースを洗い出す

- 指定された仕様書を読み、見出し・箇条書きから「操作手順」「入力値」「期待結果」を抽出する。
- 抽出結果を一覧化し、**実行前にユーザーへ提示して認識を合わせる**（仕様書の記述が曖昧な場合はここで質問する）。
- 一覧の各行が、後述のPlaywrightテストの `test()` 単位・エビデンスの連番に対応する。

### 2. パスワードの扱いを決める

- まず**環境変数名**を聞く（例: `TEST_ADMIN_PASSWORD`）。すでに `.env` にあるならそれを使う（**`.env` の中身は読まない**。値は Playwright 実行時に `process.env` 経由でのみ参照する）。
- `.env.example` に自動テスト専用のアカウント一式（例: `SEED_ADMIN_LOGIN_ID` / `SEED_ADMIN_PASSWORD` / `SEED_OPERATOR_*` / `SEED_VIEWER_*`）が用意されているプロジェクトでは、**`.env.example` はテンプレートであり秘密情報を含まないため読んでよい**。変数名とログインIDが分かれば、対応するユーザーがDBに投入済みかを軽いクエリ（`SELECT id, role FROM "User"`）で確認し、あれば新規作成せずそのまま使う。
- 環境変数が無い場合は、ユーザーに `.env.local`（Git管理外）などへの追記を提案し、**エージェントが値を代行入力しない**。チャットに平文パスワードが送られてきた場合は、以後の出力・生成ファイル・コミットメッセージに転記しない。
- Playwrightのテストコード中にパスワードをハードコードしない。必ず `process.env.<変数名>` を参照する（seedスクリプトと同じ慣習で `process.env.SEED_ADMIN_PASSWORD ?? "既定値"` の形にするのは可）。
- `playwright.config.ts` はフレームワークのように自動で `.env` を読み込まないため、テスト実行プロセスにも環境変数を渡す必要がある。Node 20.6+ なら追加パッケージ無しで次を `playwright.config.ts` の先頭に置ける。

  ```ts
  try {
    process.loadEnvFile(".env.local"); // または .env / .env.example。プロジェクトの運用に合わせる
  } catch {
    // ファイルが無い場合はスキップする
  }
  ```

  どのファイルを読むかはプロジェクトの運用による。個人のローカル設定を反映したいなら `.env.local`、`.env.example` にテスト専用アカウントの実値が書かれているならそれを指定する（本番実行には一切関わらない設定ファイルのため、`.env.example` を指定しても本番への混入リスクは無い）。既存の設定ファイルへの変更になるため、追加する前に内容を提示して承認を得る（手順3にまとめて含めてよい）。

### 3. 安全確認（必須ゲート）— ここで必ず止まる

次の4点をまとめて提示し、**ユーザーの明示的な承認を得るまで、DBの書き換え・ファイル生成・Playwrightの実行のいずれも行わない**。

| 確認項目 | 判定方法 | 停止条件 |
|---|---|---|
| Playwright未導入 | `package.json` の `devDependencies` に `@playwright/test` があるか | 無ければ導入コマンド（下記）を提示し、実行前に承認を得る |
| 対象URLが本番でないこと | `localhost` / `127.0.0.1` / 開発用ホスト名か | 本番URL（`docs/specs/99_infra/` に記載の本番ドメインや、クラウドの既定ドメイン）らしき文字列なら**停止し、ユーザーに確認する** |
| DB接続先が本番でないこと | `DATABASE_URL` のホスト部分が `localhost` / `db`（Docker Compose のサービス名）か | 外部ホスト名を含む等、本番DBらしき文字列なら**停止し、ユーザーに確認する**。値そのものはログに出さず、ホスト部分の要約だけ提示する |
| 生成するファイル | テストコードの配置予定パス、`docs/test/unit/result/<ドメイン>/テスト結果<仕様書のファイル名>/` 配下に作るエビデンス、DB確認の有無 | 手順1の一覧と合わせて提示し、「この内容で実行してよいか」を確認する |
| テストデータの一時操作 | ページング確認等で大量データが要る場合の一時作成、0件確認等で既存データを一時削除する場合の対象と復元方法 | 「テストデータの準備・後始末の方針」の節に沿って内容を具体的に提示し、承認を得る |

Playwright導入コマンド（承認後に実行）:

```powershell
pnpm add -D @playwright/test
```

```powershell
pnpm exec playwright install chromium
```

`playwright.config.ts` は既存のものをそのまま使う（`testDir: ./e2e`、`baseURL` は `E2E_BASE_URL` 環境変数で上書き可能）。設定変更が必要な場合も、変更内容を提示して承認を得てから編集する。

### 4. DBの事前状態を保存する（DB確認対象がある場合）

- DB クライアント（Prisma なら Prisma Client の `findMany`）で対象テーブルを読み出し、CSV（プロジェクトの既存依存を使う）またはJSONで書き出す。テーブルごとにCSVを分けるか、複数テーブルをまとめてJSONにするかは、テーブル数や関連の有無に応じて選ぶ。
- 事前データの準備（テストに必要な行の投入・書き換え）が必要な場合は、**その内容も手順3の承認に含めて事前に提示する**。マイグレーション系コマンドではなく、通常のデータ操作（`create` / `update`）で行う。
- 保存先とファイル名は「エビデンス保存の命名規則」に従う。
- テストデータの準備・後始末の具体的な方針は次節に従う。

### テストデータの準備・後始末の方針

ページング確認（大量データが要る）や0件確認（データを消す必要がある）は、共有のローカルDBを直接操作することが多く、他の未実施テストが使う前提データを壊すリスクがある。次の考え方で進める。

- **一時作成したデータは、そのテストケースの中で片付ける。** 例えばページング確認用に大量の行を作った場合、後続のテストケース（0件確認など）で一緒に削除してよい。テスト全体の終了時点でDBが「元々あった状態」に戻っていることを目指す。
- **0件確認のために既存データを削除する場合は、削除前に内容をバックアップし、確認後に同内容で復元する。** `test.beforeAll` で対象テーブルを `findMany` してテスト内の変数に保持し、0件確認のテストケースの中で削除・確認・復元まで行う。関連テーブル（外部キーで紐づく子テーブル）がある場合は、子→親の順に削除し、復元も親→子の順で行う。
- **`id` が自動採番の場合、復元後の `id` は元の値と一致しない。** 仕様書や `result.md` にはその旨を明記し、`id` ではなく内容（名前などの一意な値）で一致を確認する。
- **テストケースの実行順序が重要になる場合は `test.describe.serial()` を使い、破壊的な操作（全削除など）を最後のケースに置く。** 並列実行や順不同では、他のケースが削除後のデータを見てしまう。
- これらの操作は通常のデータ操作（`create` / `update` / `deleteMany`）で行い、**手順3の承認に一時作成する件数・削除対象・復元方法を具体的に含めて提示する**。

### 5. Playwrightのテストコードを作成する

- 配置場所: `e2e/<ドメイン>/<仕様書のスラッグ>.spec.ts`（例: `e2e/task/task-create.spec.ts`）。`<ドメイン>` は仕様書の保存先（`docs/test/unit/spec/<ドメイン>/`）と揃える。**再実行できるよう、通常のPlaywrightテストファイルとして作る**（使い捨てスクリプトにしない）。
- 実装方針は「Playwright実装方針」の節に従う。
- 主要な画面遷移の直後に `page.screenshot({ path: ... })` を呼び、命名規則に沿ったファイル名で保存する。

### 6. テストを実行する

```powershell
pnpm exec playwright test e2e/<ドメイン>/<ファイル名>.spec.ts
```

- 既定はヘッドレス実行。**ユーザーが「画面を見ながら」「画面表示しながら」テストしてほしいと指示した場合は `--headed` を付ける**（`pnpm exec playwright test e2e/<ドメイン>/<ファイル名>.spec.ts --headed`）。実行にはローカルの `pnpm dev` サーバーが起動している必要があるため、Bashではなく `preview_start`（`.claude/launch.json` の `dev` 等の既存設定を使う）で起動する。
- 失敗時は `--trace on` や `pnpm exec playwright show-report` で原因を確認してよい（追加のファイル生成を伴わない調査コマンドなので手順3の承認範囲内とみなす）。
- 失敗した場合、原因を切り分けたうえで手順9の「失敗時の原因候補」に記録する。テストコードの再実行はユーザーに再度断らずに行ってよいが、**DBへの書き込みを伴う再実行**（事前データの再投入など）は都度確認する。

### 7. DBの事後状態を保存する（DB確認対象がある場合）

- 手順4と同じ方法で、操作後の対象テーブルを書き出す。ファイル名は「事後」であることが分かるよう命名する。
- 事前・事後の差分（増減した行、更新された値）を目視で確認し、期待結果と一致するかを手順9のMarkdownに記載する。

### 8. 後始末を判断する

- テストで投入した事前データや、操作によって作られた行をローカルDBに残すかどうかをユーザーに確認する（次回実行時の衝突を避けたい場合は削除、証跡として残したい場合は保持）。
- エビデンス（`docs/test/unit/result/<ドメイン>/` 配下）は常に `.gitignore` 対象のためリポジトリには残らない。テストコード（`e2e/` 配下）はリポジトリに残る資産のため、そのままコミットしてよいかをユーザーに確認する。

### 9. 実行結果をMarkdownでまとめる

保存先直下に `result.md` として次の構成で作成する。

```markdown
# Playwright実行結果 — <仕様書のタイトル>

## 概要
- 仕様書: <パス>
- 対象URL: <URL>
- 実行日時: <YYYY-MM-DD HH:mm>
- テストコード: <e2e/xxx.spec.ts へのパス>

## テストケースと結果
| No | 実施内容 | 期待結果 | 実際の結果 | 判定 | エビデンス | テスト実施日時 |
|---|---|---|---|---|---|---|
| 1 | ... | ... | ... | ○ / ✕ | 001_....png | YYYY-MM-DD HH:mm |

## DB確認
| テーブル | 事前件数/値 | 事後件数/値 | 期待との一致 |
|---|---|---|---|

## 失敗時の原因候補
（失敗が無ければ「該当なし」と明記する）

## 保存したエビデンス一覧
- <保存先フォルダ配下の全ファイルを列挙>
```

### 10. 報告する

- 保存先フォルダのパスと、生成した全ファイル（テストコード・スクリーンショット・DB状態・`result.md`）を提示する。
- 手順3で承認を得た範囲を超える操作（追加のDB書き込み等）を行っていないことを明示する。

## エビデンス保存の命名規則

**保存先フォルダは `docs/test/unit/result/<ドメイン>/テスト結果<仕様書のファイル名（拡張子を除く）>/` に固定する。** テスト単位（＝仕様書1件）と設計書が1対1で対応するようにするため、聞かずにこの規則で決める。`<ドメイン>` は指定された仕様書のパス（`docs/test/unit/spec/<ドメイン>/<ファイル名>`）にすでに現れているので、そのまま使う（`create-unit-test-spec` スキルのドメイン判定規則と揃える）。例えば仕様書が `docs/test/unit/spec/task/UT_10_一覧検索.md` なら保存先は `docs/test/unit/result/task/テスト結果UT_10_一覧検索/` になる。同名フォルダが既にある場合は、上書きするか連番を付けて残すかを手順3の確認時にユーザーに確認する。

このフォルダの直下に、次の命名で保存する。連番は仕様書のテストケース順・操作順に対応させる。

| 種別 | 命名 | 例 |
|---|---|---|
| スクリーンショット | `<3桁連番>_<画面や操作の説明（日本語可・空白なし）>.png` | `001_ログイン画面.png` / `002_登録フォーム入力後.png` |
| DB事前状態 | `db_before_<テーブル名>.csv`（複数テーブルをまとめる場合は `db_before.json`） | `db_before_tasks.csv` |
| DB事後状態 | `db_after_<テーブル名>.csv`（同上は `db_after.json`） | `db_after_tasks.csv` |
| 実行結果 | `result.md` 固定 | `result.md` |
| テストコード | 保存先フォルダではなく `e2e/<ドメイン>/<スラッグ>.spec.ts` に置く（再実行用の資産のため） | `e2e/task/task-create.spec.ts` |

ファイル名は半角英数字・アンダースコア・ハイフンのみで組み立て、空白や全角記号は避ける（Windowsパス・シェル引数での事故を防ぐため）。

## Playwright実装方針

- **セレクタ**: `getByRole` / `getByLabel` / `getByText` などアクセシビリティ属性ベースを優先する（[`DESIGN.md`](../../DESIGN.md) の「インタラクティブ要素にはアクセシビリティ属性を付ける」規約と揃う）。CSSセレクタや `nth-child` のような構造依存のセレクタは避ける。
  - `getByLabel` はラベルと部分一致する他の要素（例: パスワード表示/非表示の切替ボタンが `aria-label="パスワードを表示する"` を持つ場合、`getByLabel("パスワード")` が2件ヒットして strict mode エラーになる）まで拾うことがある。曖昧なら `getByRole("textbox", { name: "..." })` のようにロールも指定して絞り込む。
- **待機**: Playwrightのオートウェイトに任せる。固定時間の `page.waitForTimeout` は使わない。画面遷移後の要素出現を `expect(locator).toBeVisible()` 等で待つ。
- **認証**: ログインが必要なテストケースが複数ある場合は、`test.beforeEach` でログイン処理を共通化するか、`storageState` を使ってログイン済み状態を使い回す。パスワードは手順2のとおり環境変数からのみ取得する。
  - **同じテストケース内でロールを切り替えてログインし直す場合**（権限差の確認など）、同じ `page` で `/login` へ再度アクセスしても既存セッションのせいでフォームが出ずタイムアウトすることがある。ロールごとに `browser.newContext()` で独立したセッションを作る。
- **アサーション**: 画面の見た目だけでなく、期待結果に挙がっている文言・件数・遷移先URLを `expect` で検証する。スクリーンショットは記録用であり、アサーションの代わりにしない。
- **命名（`describe` / `test`）**: [`TESTING.md`](../../TESTING.md) §6 の単体テストの命名規約（日本語で「大項目 → 条件 → 期待」を一文として読めるようにする）をE2Eにも準用する。
- **後始末**: `test.afterEach` でテスト固有の作成データを消すかどうかは手順8の判断に従う。自動で消す実装にする場合は、その旨をテストコードの直前コメントに一言残す。

## 安全ルールまとめ

- **本番DB・本番URLには接続しない。** 迷ったら停止してユーザーに確認する（手順3）。
- **パスワードは環境変数経由でのみ扱う。** チャット・生成ファイル・コミットメッセージに平文で残さない（手順2）。
- **ファイル生成（テストコード・エビデンス・DBへの書き込み）は、実行前にまとめて承認を得てから行う**（手順3）。承認範囲を超える追加の書き込みは都度確認する。
- **Playwright未導入なら、導入コマンド実行前に承認を得る**（手順3）。
- `.env` の読み取りは既存の権限ポリシー（[`docs/agent_permissions.md`](../agent_permissions.md)）で禁止されている。DB接続情報が必要な場合も、値そのものではなくホスト部分の要約や、実行結果（成功/失敗）で判断する。
