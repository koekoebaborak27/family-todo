# スキル: Vitestの単体テストを作成・実行する

指定された実装ファイルについて、`TESTING.md` の方針に従いVitestの単体テストコード（`*.test.ts`、DB統合が必要なら `*.int.test.ts`）を作成し、`pnpm test` が通るまで直す。

このファイルが手順の**正本**。Claude Code / GitHub Copilot / Codex の各入口ファイルは、ここを読ませるだけの薄いラッパーであり、手順を複製しない。Claude Codeではサブエージェント（独立した会話）としても呼べる。その場合、試行錯誤の過程（失敗→直す→再実行の繰り返し）は本体の会話に残さず、完了時の要約だけを返すことを想定している（詳細は末尾「3ツールでの実行のされ方」）。

## このスキルの中核（何を担保するか）

| 観点 | 内容 | 対策 |
|---|---|---|
| `TESTING.md` の方針からの逸脱を防ぐ | 独自流儀でテストを書くと、既存テストとの統一が崩れる | コロケーション配置・レイヤーごとの濃淡・命名規約・テストデータの作り方を必ず `TESTING.md` から読み、それに従う（手順3） |
| 書く必要のない層への無駄な作成を防ぐ | `TESTING.md` では `ui/` や単純な `repository.ts` は原則テストを書かない層としている | 手順1でレイヤーを判定し、対象外なら理由を報告して終了する |
| DBの汚染・破壊を防ぐ | DB統合テストの後始末を忘れると開発DBが汚れる、禁止コマンドを使うと壊れる | 後始末（truncateまたはロールバック）を徹底し、`docs/agent_permissions.md` の禁止コマンドは使わない |
| 試行錯誤の垂れ流しを防ぐ | 失敗と修正を繰り返す過程をそのまま呼び出し元に返すと、会話のトークンを圧迫する | 完了時は要約のみを返す（手順6） |

## 使うタイミング

- 「〇〇のVitestテストを書いて」「単体テストを実行して直して」と依頼されたとき
- 実装後に `service.ts` / `validation.ts` / `rbac.ts` 等の単体テストを揃えたいとき
- 既存テストが壊れている、または `pnpm test` が失敗しているときに直してほしいとき

## 受け取る情報（事前確認）

| 項目 | 必須 | 備考 |
|---|---|---|
| 対象ファイル | ○ | 例: `src/modules/master/service.ts` |
| 関連する単体テスト仕様書 | △ | `docs/test/unit/spec/` 配下にあれば渡す（`create-unit-test-spec` スキルの成果物。あればテストケースの元ネタにする） |
| DB統合テストが必要か | △ | 不明なら手順1で `TESTING.md`「2. レイヤーごとの濃淡」表から判定する |

## 手順

### 1. 対象を確認し、書くべき層か判定する

- 対象ファイルを読み、`TESTING.md`「2. レイヤーごとの濃淡」表と照合する。「✕当面スキップ」「△原則書かない」に該当し、かつ複雑なクエリ・トランザクション境界などの例外条件にも当てはまらない場合は、その旨を報告して終了する（無理にテストを作らない）。
- 関連する単体テスト仕様書（`docs/test/unit/spec/**`）があれば読み、テストケースの元ネタにする。無ければコードから直接観点を拾う。

### 2. 既存テストの有無を確認する

- 対象ファイルと同階層に `<name>.test.ts`（または `<name>.int.test.ts`）が既にあるか確認する。無ければ新規作成、あれば追記・修正する。

### 3. `TESTING.md` の規約に従って書く

- **配置**: 対象ファイルと同階層に置く（`__tests__/` への集約はしない）。
- **命名・構成**: `describe` を「大項目 → 条件 → 期待」の3階層にし、すべて日本語で書く（`TESTING.md`「6. 命名」）。ファイル冒頭に対象と目的をコメントで書く。
- **テストデータ**: `service` 層は実DB不要、型付きファクトリで `repository` のモック戻り値を組み立てる。`repository` 層の複雑クエリのみ実DB＋フィクスチャを使い、`*.int.test.ts` に分離する（`TESTING.md`「7. テストデータ」）。
- **観点**: 正常系・業務分岐・異常系（`AppError` の `code` とメッセージまで正確に転記）・境界値を、対象レイヤーの表（`TESTING.md`「2.」）に沿って拾う。

### 4. `pnpm test` を実行し、通るまで直す

- `*.int.test.ts` を含む場合は、先にローカルDBが起動していることを確認する（Docker を使う構成なら `docker compose -f docker/docker-compose.yml up -d db`）。
- 失敗したら原因を切り分けて直す。**何度か直しても通らない場合は、無限に繰り返さず、原因の推測と試したことを要約してユーザーに報告する**（対象コード自体に疑わしい不具合がある可能性を含めて報告する。テストを実装の不具合に合わせて歪めない）。

### 5. 網羅を自己確認する

- `pnpm exec vitest list` でテスト名の一覧を確認し、`TESTING.md`「6.4」および単体テスト仕様書（あれば）のテストケース一覧と突き合わせ、観点の抜けがないか確認する。

### 6. 要約して返す

呼び出し元には次を簡潔に要約して返す。試行錯誤の過程（何回失敗したか等）は返さない。

- 作成・変更したテストファイルのパス
- `pnpm test` の実行結果（成功件数、対象テスト名の概要）
- 直した内容の要点（既存テストを修正した場合）
- 手順1で対象外と判定して終了した場合は、その理由

## 安全ルール

- `docs/agent_permissions.md` の禁止コマンドを厳守する（`pnpm db:reset*` / `prisma migrate reset*` 等は実行しない）。`.env` は読まない。
- DB統合テストは、各テストの後始末（truncateまたはトランザクションロールバック）を必ず行う。`prisma:seed` の中身に依存したテストデータを作らない。
- テスト作成の過程で実装コード自体の不具合に気づいても、無断で実装を修正しない。テスト結果の要約と合わせてユーザーに報告する。

## 3ツールでの実行のされ方

同じ手順書でも、ツールによって「独立した場で実行され、要約だけが返る」という分離の効果が異なる。

| ツール | 起動のされ方 | 分離の実態 |
|---|---|---|
| Claude Code | descriptionの一致による自動委譲、または `@agent-create-vitest-test` / 自然言語での明示指定 | 独立した会話で実行し、要約のみ本体へ返る（真の分離。トークン削減効果が確実に得られる） |
| GitHub Copilot | Copilot Chat のエージェント切替ドロップダウンから手動選択 | 選択後は会話全体がそのエージェントになる。呼び出し元へ要約だけを返す仕組みは無い |
| Codex | 既存の「スキル」と同じ、説明文による自動起動 | 同一セッション内で実行される（真の分離は未対応。Codexにプロジェクト同梱できる独立サブエージェント機構が現状無いため） |

トークン削減という目的が確実に得られるのはClaude Codeのみ。Copilot / Codexでは「役割ごとに手順を切り替えて実行できる」以上の効果は期待しない。
