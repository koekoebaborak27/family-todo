# スキル: 単体テスト仕様書をMarkdownで作成する

実装済みまたは実装予定の機能について、ソースコード・設計書・画面仕様・API仕様・DBスキーマ・ユーザーからの説明を読み取り、Markdown形式の単体テスト仕様書を作成する。作成した仕様書は、後続の [`playwright-evidence-test`](playwright-evidence-test.md) スキルによる画面操作テストや、手動テストでそのまま使える粒度にする。

このファイルが手順の**正本**。Claude Code / GitHub Copilot / Codex の各入口ファイルは、ここを読ませるだけの薄いラッパーであり、手順を複製しない。

## このスキルの中核（何を担保するか）

| 観点 | 内容 | 対策 |
|---|---|---|
| 仕様の捏造を防ぐ | コードにも設計書にも無い挙動を推測で埋めると、仕様書自体が誤った正解になる | 判断できることは自分で調べ、判断できないことは必ずユーザーに確認する（手順3） |
| Playwrightで再現できない手順を防ぐ | 「それっぽく見える」だけで操作手順・期待結果が曖昧だと、後続の自動化で実装し直しになる | セレクタで拾える言葉・検証可能な値で書く（「Playwright自動化を見据えた書き方」） |
| 観点の抜けを防ぐ | 正常系だけの仕様書はテストとして不十分 | 「テスト観点チェックリスト」を毎回全項目チェックする |
| 無承認のファイル作成を防ぐ | 仕様書は成果物としてリポジトリに残る | 保存先とファイル名を提示し、作成可否の承認を得てから書く（手順4） |

## 使うタイミング

- 「単体テスト仕様書をMarkdownで作って」と依頼されたとき
- 実装内容からテスト観点を洗い出したいとき
- 画面、API、サーバ処理、DB処理のテストケースを整理したいとき
- 後でPlaywrightによる画面操作テストに使える仕様書を作りたいとき
- 正常系、異常系、境界値、権限、入力制御、DB更新内容を漏れなく確認したいとき

## 受け取る情報（事前確認）

| 項目 | 必須 | 備考 |
|---|---|---|
| 対象機能 | ○ | 例: 「予定の削除（TODO-04）」のように、機能名と画面IDが分かる形で |
| 対象ファイル | △ | 分かっていれば聞く。無ければ手順1でエージェントが調べる |
| 対象画面URL または API パス | 画面/APIがある場合は○ | Playwright自動化での `対象URL` に対応 |
| 関連する設計書・仕様書 | △ | `docs/specs/**` にあれば場所を聞く。無ければ手順1で探す |
| DBテーブル | DB更新を伴う場合は○ | Playwright自動化での `DB確認対象` に対応 |
| 仕様書のファイル名 | ○ | `UT_` を先頭に付けたファイル名にする。設計書があれば `UT_<設計書と同じファイル名>` を使う（例: 設計書が `10_一覧検索.md` なら `UT_10_一覧検索.md`）。保存先は `docs/test/unit/spec/<ドメイン>/<ファイル名>` に固定する（テスト単位のフォルダは作らない。聞かない）。`<ドメイン>` は対象機能が属する `src/modules/` 配下のディレクトリ名に合わせる。関係の深い複数モジュールをまとめて 1 つのドメイン名で扱ってもよい。既存のどのドメインにも当てはまらない新しいモジュールを追加した場合は、そのモジュール名をそのままドメイン名にする |

**不明点は推測で埋めない。** コードや既存ドキュメントから判断できることは自分で調べ、判断できないことだけをユーザーに確認する（手順3）。

## 手順

### 1. 対象を確認し、関連資料を集める

- 対象機能・対象画面/APIをユーザーに確認する。対象ファイルが未指定なら、機能名や画面IDから `src/modules/<機能>/` を探す。
- 関連する設計書を探す。基本設計書は `docs/specs/02_basic-design/<機能>/` 配下に画面ごとの Markdown（例: `docs/specs/02_basic-design/<機能>/11_新規登録.md`）として置かれ、末尾に「テスト方針」節を持つことがある。**あれば最優先で読む**（そのプロジェクトが既にテスト観点を検討済みの証拠のため）。
- DBスキーマ（Prisma なら `prisma/schema.prisma`）を読み、対象テーブルのカラム・制約（一意制約 / NOT NULL / リレーション）を確認する。

### 2. ソースコードから機械的にテスト観点を拾う

このプロジェクトはレイヤーごとに責務が分かれている（`src/AGENTS.md`）。**レイヤーごとに拾える観点が決まっている**ので、総当たりで読むのではなく対応表に沿って読む。

| レイヤー | ファイル | 拾える観点 |
|---|---|---|
| 入力検証 | `validation.ts`（Zod） | 必須/任意、最大文字数、形式、境界値、未入力時のエラー |
| 業務ロジック | `service.ts` | 正常系の分岐、重複・存在しないID等での `AppError` 発生条件（`code` は `Errors.NOT_FOUND` / `UNAUTHORIZED` / `FORBIDDEN` / `VALIDATION_ERROR` / `CONFLICT` またはモジュール独自キー） |
| 認可 | `rbac.ts` / `route-guard.ts` / `actions.ts` 冒頭の認可チェック | ロールごとの権限差、権限不足時の挙動 |
| DB入出力 | `repository.ts` | 更新されるテーブル・カラム、DB制約違反の起きうる操作 |
| 画面 | `ui/*.tsx` | クリック対象、入力項目、活性/非活性制御、確認ダイアログ、表示メッセージ、遷移先 |

`AppError` の `code` と `userMessage` は、そのままテストケースの「期待結果」の文言・判定条件になる。**コードを実際に読んで正確な文言・コードを転記する**（言い換えない）。

### 3. 不明点をユーザーに確認する

コードにも設計書にも根拠がない場合のみ質問する。よくある例:

- 権限マトリクスがコード上は実装されているが、設計書に記載が無く「意図した仕様か実装の都合か」判断できない
- 境界値の具体的な数値（最大文字数・上限件数）がコードに定数として無く、設計書にも書かれていない
- 異常系の挙動（例: 二重送信時の扱い）がコード上分岐が無く未実装に見える

質問は**手順1・2で調べ切った後にまとめて**行う。1問ずつ都度聞くと仕様書作成が止まるため、一覧化して聞く。

### 4. 保存先を確認し、作成可否の承認を得る（必須ゲート）

仕様書はリポジトリに残る成果物のため、書き始める前に次を提示し、承認を得る。

- 仕様書のファイル名（例: `UT_10_一覧検索.md`）と、そこから決まる保存先（例: `docs/test/unit/spec/<ドメイン>/UT_10_一覧検索.md`）
- 対象範囲（今回のテストケース一覧の粒度・件数の見込み）
- 手順3で確認が必要だった不明点と、その回答（無ければ「無し」と明記）

承認を得るまでファイルを作成しない。同名のファイルが既にある場合は、上書きすることも明示する。

### 5. 標準フォーマットで仕様書を作成する

「仕様書の標準フォーマット」の節をそのまま使う。**見出し構成・表の列は変更しない**（後続の `playwright-evidence-test` スキルがこの構成を前提に読むため）。テストケースには機能内で一意な `TC-001` 形式の番号を振り、「4. テストケース一覧」と「5. DB確認内容」で同じ番号（No列）を使う。

### 6. テスト観点チェックリストで網羅を確認する

「テスト観点チェックリスト」の節にある観点ごとに、該当するテストケースが最低1件あるかを確認する。対象機能の性質上そもそも当てはまらない観点（例: 画面が無いAPIでの「画面表示」）は、その旨を「7. 補足」に一言残して省略してよい。

### 7. Playwrightで再現できる粒度に書けているか自己確認する

「Playwright自動化を見据えた書き方」の節に沿っているかを見直す。特に次の3点は書いてから読み返す。

- 操作手順が「ボタン名」「ラベル名」など `getByRole` / `getByLabel` / `getByText` でそのまま拾える言葉になっているか（「画面右上のボタンを押す」のような位置依存の表現になっていないか）
- 期待結果が検証可能な具体的な文言・値・件数になっているか（「正しく表示される」「エラーになる」のような曖昧な言い方になっていないか）
- 未確定のまま残った事項が本文中に埋もれず、すべて「6. 未確定事項」に回収されているか

### 8. 提示・保存する

- 手順4で承認された保存先にファイルを作成する。
- `playwright-evidence-test` スキルへそのまま引き継げるよう、対象URL・ログイン想定ユーザー・DB確認対象テーブルを一覧化して案内する（次にそのスキルを呼ぶときに聞かれる項目と対応させる）。

## テスト観点チェックリスト

| 観点 | 確認する内容 | 主な情報源 |
|---|---|---|
| 正常系 | 代表的な入力・操作で期待どおり完了するか | `service.ts` の正常系分岐、設計書 |
| 異常系 | 存在しないID、重複、権限不足、不正な状態遷移でどう失敗するか | `service.ts` の `AppError` 発生条件 |
| 境界値 | 最大文字数、上限/下限件数、0件・1件・複数件 | `validation.ts`、設計書の制約記載 |
| 未入力 | 必須項目を空にしたとき | `validation.ts` |
| 最大文字数 | 上限ちょうど／超過 | `validation.ts`、`prisma/schema.prisma` のカラム長 |
| 重複 | 一意制約のある値を重複させたとき | `prisma/schema.prisma` の `@unique`、`service.ts` の重複チェック |
| 存在しないID | 削除・更新・詳細表示で対象が無いとき | `service.ts` の `NOT_FOUND` 系 |
| 権限不足 | 権限の無いロールで操作したとき | `rbac.ts` / `route-guard.ts` |
| DB制約違反 | 外部キー制約・NOT NULL制約に触れる操作 | `prisma/schema.prisma` |
| 画面表示制御 | ボタンの活性/非活性、確認ダイアログの表示条件、一覧の並び替え・ページング | `ui/*.tsx` |

## Playwright自動化を見据えた書き方の注意

作成した仕様書は `playwright-evidence-test` スキルがそのまま読む前提で書く。

- **操作手順**はボタン名・ラベル名・表示文言など、`getByRole` / `getByLabel` / `getByText` でそのまま拾える言葉で書く。画面上の位置（「右上の」「一番下の」）だけを頼りにした表現は避ける。
- **期待結果**は検証可能な文言・値・件数で書く。「エラーになる」ではなく「『分類名は必須です』とエラーメッセージが表示される」のように、コードから転記した実際の文言を使う。
- **5. DB確認内容**の「テーブル」「条件」「カラム」「期待値」は、`playwright-evidence-test` スキルがDB状態のCSV/JSON出力と突き合わせる列になる。テーブル名・カラム名はスキーマ定義（Prisma なら `prisma/schema.prisma`）どおりに書く。DB変化が無いテストケースは「該当なし（DB変化なし）」と明記する。
- **4. テストケース一覧**の「エビデンス」列は `playwright-evidence-test` スキルの命名規則（`docs/skills/playwright-evidence-test.md` の「エビデンス保存の命名規則」）を先取りして書いてよい（例: `001_削除確認ダイアログ.png`）。厳密な連番は実行時に確定するため、ここでは「何を撮るか」が分かれば十分。

## 安全ルール

- **推測で仕様を埋めない。** コード・既存ドキュメントで判断できないことは、手順3でユーザーに確認してから書く。
- **ファイル生成前に保存先とファイル名を提示し、作成可否の承認を得る**（手順4）。承認を得るまで書き始めない。
- 仕様書作成の過程は**読み取りのみ**。ソースコード・DB・設定ファイルを変更しない（変更が必要な発見があれば、仕様書の「7. 補足」に書いてユーザーへ報告するに留める）。
- 前提条件に本番の実データ・本番URLを書かない。`playwright-evidence-test` スキルは本番DB・本番URLへの接続を拒否するため、仕様書側もローカル/検証環境を前提に書く。
