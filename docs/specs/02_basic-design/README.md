# 02_basic-design/ — 基本設計書

機能ごとにディレクトリを作り、画面・処理の単位でファイルを分ける。

```
02_basic-design/
├─ <機能名>/
│  ├─ README.md        ← この機能の索引
│  ├─ 00_<機能名>共通.md ← 用語・共通仕様・権限
│  ├─ 01_データベース.md ← この機能が使うテーブル
│  ├─ 02_API仕様.md     ← REST APIエンドポイント一覧
│  ├─ 10_<画面名>.md
│  └─ 11_<画面名>.md
└─ 画面遷移図.md         ← 全体の画面遷移（.mmd + .svg。docs/diagrams.md 参照）
```

各画面のファイルに書くこと: 画面の目的、表示項目、入力チェック、操作と遷移先、権限による差、エラー時の表示文言、DB への影響。

**エラーメッセージなどの文言は実際に表示する文字列をそのまま書く。** 単体テスト仕様書（`docs/test/unit/spec/`）がここから転記するため。

## インフラ関連事項の技術検証

要件定義書「[16. 技術的制約](../01_requirements/family-todo/01_家族todo共有アプリ.md)」で「基本設計フェーズで確定する」とした項目。**詳細設計の前提が変わりうるため、画面・API・DB の詳細設計に着手する前に検証する。**

いずれも結果が出たら「結果」欄を書き換え、採用した構成を該当の設計書（`family-todo/02_API仕様.md` など）へ反映する。

### 検証1 Cloudflare Workers 上で Express が動くか

| 項目 | 内容 |
| --- | --- |
| 何を確かめるか | Backend（Express）を Cloudflare Workers 上で動かせるか。Express とその周辺が使う Node.js 標準の機能（`http`・`stream`・`buffer` など）が Workers 側で用意されているかどうかで決まる |
| 確かめ方 | 検証用の小さな Worker を作り、Express のアプリを 1 本載せて `wrangler dev` で起動する。GET と POST を 1 つずつ用意し、ローカルで応答が返ることと、`wrangler deploy` で実際の Workers 上でも同じ応答が返ることを確認する。あわせて Cloudflare D1 のバインディング経由でテーブルを 1 つ読み書きできるかも確認する |
| ダメだった場合の代替案 | Pages Functions 等の別構成へ切り替える。その場合、Express を前提にした書き方（ミドルウェア・ルーター）は使えなくなるため、API の実装方針を基本設計へ差し戻して決め直す |
| 結果 | **動いた（2026-08-31）。** `nodejs_compat` フラグを立てた Worker に `cloudflare:node` の `httpServerHandler` で Express アプリを載せる構成で、GET・POST（日本語ボディ含む）・`express.Router()` によるパス変数・ミドルウェア・404ハンドラのいずれも問題なく動作した。D1 も `env.DB` から通常どおり読み書きできた。`wrangler dev`（ローカル）と `wrangler deploy`（実機の Workers）の両方で同じ結果を確認済み。代替案（Pages Functions 等への切り替え）は不要。詳細 → [`docs/todo/notes/`](../../todo/notes/README.md) |

### 検証2 Web Push のライブラリが Workers ランタイムで動くか

| 項目 | 内容 |
| --- | --- |
| 何を確かめるか | Web Push（VAPID 方式）の送信処理を Workers 上で実行できるか。この種のライブラリは Node.js の `crypto` を使って署名するものが多く、Workers 側で同じことができるかどうかが分かれ目になる |
| 確かめ方 | 検証1 で作った Worker から、VAPID の鍵を使って自分のブラウザへ通知を 1 通送る。鍵の生成・署名・送信のどこで失敗するかまで確認する |
| ダメだった場合の代替案 | Workers の標準機能（Web Crypto）だけで署名を組み立てて自前で送信する。それも難しい場合は、通知の送信部分だけを Workers 以外の実行基盤へ分ける |
| 結果 | **動いた（2026-08-31）。** npm の `web-push`（VAPID の鍵生成・署名・送信を行う標準的なライブラリ）を追加コード無しでそのまま利用できた。検証1 の Worker から実際のブラウザ（Chrome）へ通知を1通送信し、受信を確認済み。代替案（Web Crypto での自前実装、送信処理の分離）は不要。詳細 → [`docs/todo/notes/`](../../todo/notes/README.md) |

### 検証3 期限接近と期限超過の通知を送る定期実行の間隔をいくつにするか

| 項目 | 内容 |
| --- | --- |
| 何を確かめるか | Cloudflare Cron Triggers を何分おきに動かすか。要件ではリマインドを「期限の何時間前・何日前」で指定するため、通知の遅れがユーザーに気づかれない範囲に収まる最長の間隔を選ぶ |
| 確かめ方 | 5 分おき・15 分おき・1 時間おきを候補として、検証用の Worker に Cron Triggers を設定して実際に動かす。設定した時刻からどれだけ遅れて実行されるか、1 回あたりの処理時間と実行回数が無料枠に収まるかを見て決める |
| ダメだった場合の代替案 | Cron Triggers の間隔を短くしても遅れが許容できない場合は、通知の送信予定時刻を先に計算して保存しておき、定期実行では保存済みの予定を拾うだけにする |
| 結果 | **15分おきに確定（2026-08-31）。** 1分おきの Cron Triggers を実機で8分間動かして計測したところ、予定時刻からの遅れは6回とも1秒未満（896ms〜1037ms、平均約936ms）で、実行間隔に関わらず無視できる小ささだった。無料枠（Workers Free: 1日10万リクエストまで）も、5分おき（1日288回）・15分おき（1日96回）・1時間おき（1日24回）のいずれでも消費は微々たるもので制約にならない。そのため間隔の選定は Cron 自体の遅れではなく通知の粒度で決め、「期限の何時間前・何日前」という要件の粒度に対して体感的に十分正確で実行回数も抑えられる 15分おき を採用した。代替案（送信予定時刻の事前計算）は不要。詳細 → [`docs/todo/notes/`](../../todo/notes/README.md) |
