# Google OAuthログインフローとセッション管理

関連: 基本設計 [`00_family-todo共通.md`](../../02_basic-design/family-todo/00_family-todo共通.md)「認証・アクセス制御」、[`02_API仕様.md`](../../02_basic-design/family-todo/02_API仕様.md)「認証」、[`10_ログイン.md`](../../02_basic-design/family-todo/10_ログイン.md)、[`01_データベース.md`](../../02_basic-design/family-todo/01_データベース.md)（`sessions`）。

## ログインフロー（Authorization Codeフロー）

1. Frontendの「Googleでログイン」ボタンから、Googleの認可画面へ遷移する。
2. ユーザーがGoogle側で許可すると、認可コードを持ってFrontendへ戻る。
3. Frontendは受け取った認可コードを`POST /auth/google/callback`へ渡す。
4. Backendは次を行う。
   1. 認可コードをGoogleのトークンエンドポイントへ渡し、`id_token`（および`access_token`）と交換する。
   2. `id_token`をGoogleの公開鍵（JWKS）で検証する（署名・発行者・有効期限・audience＝このアプリのクライアントIDを確認する）。
   3. 検証できた`id_token`から`sub`（Googleアカウントの一意なID）・`email`・氏名を取り出す。
   4. `users`を`google_sub`で検索する。無ければ新規作成する（[`10_ログイン.md`](../../02_basic-design/family-todo/10_ログイン.md)「8. DBへの影響」のとおり）。
   5. 新しいセッションを発行する（下記「セッションの発行」）。
5. Backendはセッションを表すCookieをレスポンスに付け、成功をFrontendへ返す。Frontendはこの後、所属グループの有無で画面を振り分ける（[`10_ログイン.md`](../../02_basic-design/family-todo/10_ログイン.md)「5. 操作と遷移先」）。

Googleでの拒否・中断、認可コードの検証失敗時のエラー文言は[`10_ログイン.md`](../../02_basic-design/family-todo/10_ログイン.md)「7. エラー時の表示文言」のとおり。

## セッションの発行

`sessions`テーブル（[`01_データベース.md`](../../02_basic-design/family-todo/01_データベース.md)参照）に1行追加する。

| 列 | 値 |
| --- | --- |
| `id` | 推測不可能なランダム値（暗号学的乱数、32バイト以上を想定） |
| `user_id` | ログインしたユーザー |
| `expires_at` | 現在時刻の90日後 |
| `created_at` | 現在時刻 |

`id`をCookieの値としてレスポンスに設定する。Cookie属性は次のとおり。

| 属性 | 値 | 理由 |
| --- | --- | --- |
| `HttpOnly` | あり | JavaScriptから読めないようにし、XSSでの窃取を防ぐ |
| `Secure` | あり | HTTPS以外では送信しない |
| `SameSite` | `None` | Frontend（Next.js）とBackend（Express/Workers）が別オリジンになる可能性があるため。本番のドメイン構成が同一オリジンに決まった場合も`None`のまま動作する |
| `Path` | `/` | |
| 有効期限 | `expires_at`と同じ90日 | |

## セッションの検証（認証が必要なAPI全般）

1. リクエストのCookieからセッションIDを取り出す。無ければ`401`。
2. `sessions`を`id`で検索する。該当が無い、または`expires_at`が現在時刻より前なら`401`。
3. 検証できたら、そのリクエストの処理を続ける前に`sessions.expires_at`を現在時刻の90日後へ更新する（スライディングセッション。使い続けている家族メンバーが再ログインを求められないようにするため）。

## ログアウト

`POST /auth/logout`が呼ばれたら、対応する`sessions`の行を削除し、レスポンスでCookieを失効させる（`Max-Age=0`で上書き）。

## CSRF対策

このAPIはJSON（`Content-Type: application/json`）のみを受け付け、CORSは許可オリジンをFrontendのオリジンのみに限定する。ブラウザは`application/json`のクロスオリジンリクエストで必ずプリフライト（`OPTIONS`）を送るため、許可していないオリジンからの状態変更リクエスト（フォーム等の単純リクエストでは`application/json`を指定できない）は、Cookieが自動送信される前にCORSでブロックされる。この方式により、`SameSite=None`でも追加のCSRFトークンなしでCSRFを防げる。

## DBへの影響

| タイミング | 影響 |
| --- | --- |
| ログイン成功時 | `sessions`に1件追加する |
| 認証付きAPI呼び出しのたび | 対応する`sessions`行の`expires_at`を更新する |
| ログアウト時 | 対応する`sessions`行を削除する |
| セッション期限切れ後のアクセス | 該当行が残っていても`expires_at`超過として扱う（削除は行わず、期限切れ行として無視する。定期的な掃除は運用タスクとし、この設計では扱わない） |
