# 期限接近・期限超過の通知バッチ処理

関連: 基本設計 [`02_API仕様.md`](../../02_basic-design/family-todo/02_API仕様.md)「定期処理（バッチ）」、[`01_データベース.md`](../../02_basic-design/family-todo/01_データベース.md)（`todos`・`notification_settings`・`push_subscriptions`）、技術検証（[`02_basic-design/README.md`](../../02_basic-design/README.md#インフラ関連事項の技術検証)）。

## 対象範囲

Cloudflare Cron Triggers（**15分おき**）で実行する、`due_soon`（期限接近）・`overdue`（期限超過）の2種類の通知送信を扱う。`todo_added`・`assignee_set`はToDo作成・担当者設定のAPI呼び出しに紐づくリアルタイム通知であり、このバッチの対象外。

## 前提となるDBの列

`todos`に次の2列を持つ（追加済み。詳細は[`01_データベース.md`](../../02_basic-design/family-todo/01_データベース.md)の`todos`）。

| 列 | 用途 |
| --- | --- |
| `due_soon_notified_at` | 期限接近通知をこの期限に対して送信済みか（NULL=未送信） |
| `overdue_notified_at` | 期限超過通知をこの期限に対して送信済みか（NULL=未送信） |

いずれも次のタイミングでNULLに戻す。

- ToDoの`due_at`が変わったとき（`PATCH /todos/:id`での編集、繰り返しToDoの次回進行 → [`10_繰り返しToDoの期限計算.md`](10_繰り返しToDoの期限計算.md)）
- `POST /todos/:id/incomplete`で未完了に戻したとき

## 対象の絞り込み

日付・時刻の判定は[`10_繰り返しToDoの期限計算.md`](10_繰り返しToDoの期限計算.md)と同じくJSTで行う（`remind_before_unit`が`hours`/`days`のいずれでも、`due_at`からの差分計算はUTCのまま行ってよい。時差の変換が要るのは日付境界の判定だけ）。

### 期限接近（due_soon）

条件をすべて満たす`todos`を抽出する。

```sql
SELECT * FROM todos
WHERE status = 'incomplete'
  AND due_at IS NOT NULL
  AND due_soon_notified_at IS NULL
```

各行について、担当者ごとに次を判定する。

1. 担当者が非登録メンバーの場合は、その担当に紐づく`is_follower = true`の登録ユーザーを通知先とする（担当者が登録ユーザーならその人自身）。
2. 通知先ユーザーの`notification_settings`（`notification_type = 'due_soon'`）が`enabled = true`であること。
3. `notify_at = due_at - (remind_before_value を remind_before_unit で換算した時間)` を求め、`notify_at <= 現在時刻 < due_at` であること（＝通知すべき時刻を過ぎていて、期限はまだ来ていない）。

3を満たす担当者が1人でもいれば、そのToDoは今回のバッチで処理する対象とし、条件を満たした担当者全員へ送信する（3を満たさない担当者には送らない）。

### 期限超過（overdue）

```sql
SELECT * FROM todos
WHERE status = 'incomplete'
  AND due_at IS NOT NULL
  AND due_at <= 現在時刻
  AND overdue_notified_at IS NULL
```

各行の担当者のうち、`notification_settings`（`notification_type = 'overdue'`）が`enabled = true`の人（非登録メンバーの場合は`is_follower`の登録ユーザー）へ送信する。**期限を過ぎた直後に1回だけ**送る（それ以降、完了するかToDoの期限が変わるまで再送しない）。

## 重複送信の防止

`due_soon_notified_at`・`overdue_notified_at`をバッチ内で判定に使い、**対象条件を満たした時点で（実際に何人へ送れたかに関わらず）現在時刻を書き込む**。これにより、次回以降のバッチでは抽出条件に該当しなくなり、15分間隔の実行が重なっても二重送信されない。

- 通知設定がOFFで送信対象者が1人もいなかった場合も、条件を満たした時点でフラグを立てる（後から設定をONにしても、その期限に対する通知の機会は再来しない）。これは実装を単純に保つための割り切りとする。

## Push送信失敗時の扱い

各通知対象ユーザーの`push_subscriptions`を全件取得し、購読ごとに送信を試みる。

| 結果 | 扱い |
| --- | --- |
| 送信成功 | 何もしない |
| `410 Gone` / `404 Not Found`（購読が失効） | 該当する`push_subscriptions`の行を削除する |
| それ以外の失敗（一時的なネットワークエラー等） | 何もしない（リトライしない）。次の15分後の実行では別の通知種別・対象として再評価されるだけで、この送信自体はやり直さない |

## バッチ全体の処理順序

1. `due_soon`の対象を抽出し、担当者ごとに送信・`due_soon_notified_at`を更新する。
2. `overdue`の対象を抽出し、担当者ごとに送信・`overdue_notified_at`を更新する。
3. 1・2それぞれの送信で、購読が失効していた`push_subscriptions`があれば削除する。
