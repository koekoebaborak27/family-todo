# 単体テスト仕様書: 個人設定

## 1. テスト対象

- 対象機能: 個人設定
- 対象画面またはAPI: 個人設定画面（`/settings`）
- 対象ファイル: `apps/frontend/src/modules/settings/ui/settings-screen.tsx`、`apps/frontend/src/modules/settings/api-client.ts`、`apps/frontend/src/modules/settings/service.ts`、`apps/frontend/src/modules/settings/push-subscription.ts`、`apps/backend/src/modules/settings/service.ts`、`apps/backend/src/modules/settings/routes.ts`、`apps/backend/src/modules/settings/validation.ts`、`apps/backend/src/modules/push-subscription/routes.ts`
- 関連DBテーブル: `users`、`notification_settings`、`push_subscriptions`、`sessions`
- 関連設計書: [`22_個人設定.md`](../../../../specs/02_basic-design/family-todo/22_個人設定.md)（本テスト仕様書作成にあわせて、設計書と実装の食い違い2点を解消している。詳細は「7. 補足」参照）

## 2. 前提条件

- 実行環境: ローカル（`pnpm dev:backend` = http://localhost:8787 / `pnpm dev:frontend` = http://localhost:3000）
- ログインユーザー: 実際のGoogleアカウントは使用せず、[`ローカルD1へのセッション投入によるUI確認.md`](../../../../todo/notes/ローカルD1へのセッション投入によるUI確認.md)の手順でログイン済み状態を再現する
- 権限: 無し（「6. 権限による差」のとおり、すべて自分自身の設定のみを扱う。家族グループへの所属も問わない）
- 事前DB状態（共通シード。以下の記号を各テストケースの「前提条件」列で参照する）:
  - `U1`: `users`に1件、有効な`sessions`を持つ（ログイン中のユーザー本人。表示名「テスト太郎」、`default_due_time = '20:00'`）。アカウント作成時のseedにより`notification_settings`は4種別とも`enabled = 1`（`due_soon`のみ`remind_before_value = 1`・`remind_before_unit = 'days'`）で投入済み
  - 使用するテストデータ: 上記`U1`のみ（家族グループは不要）

## 3. テスト観点

- 正常系: 初期表示（プロフィール・通知設定・期限の扱い・Push状態・戻るボタン）、表示名の保存、通知スイッチの切り替え、リマインドのタイミング変更、基準時刻の変更、Push通知の許可・購読登録、ログアウト
- 異常系: 画面表示時の未認証（401）、各操作中の未認証（401）、表示名・通知設定・基準時刻の保存失敗、通知の拒否、購読情報の登録失敗
- 境界値: 表示名の未入力、20文字ちょうど／21文字
- 権限: 該当なし（「6. 権限による差」のとおり差が無いため。「7. 補足」に記載し省略する）
- DB更新: `users.display_name`・`users.default_due_time`の更新、`notification_settings`の`enabled`・`remind_before_value`・`remind_before_unit`の更新、`push_subscriptions`への追加
- 画面表示: 「期限が近づいたとき」OFF時のタイミング選択欄の操作不可化、Push通知受け取り状態の4パターン（許可済み／未設定／拒否／iOS未インストール）、送信中のボタン操作不可

## 7. 補足

- 権限による差は無い（「6. 権限による差」のとおり）ため、権限観点のテストケースは設けていない。
- 各操作（表示名の保存・通知設定の切り替え・リマインドのタイミング変更・基準時刻の変更・Push許可）中の401（セッション失効）は、当初`loadSettings`と通知スイッチの切り替えにしか実装されておらず、それ以外の操作は操作別の汎用失敗メッセージを表示するのみでログイン画面へ遷移しない状態だった（ToDo詳細・家族グループ設定で見つかったのと同じパターン）。ユーザー承認のうえ設計書どおりの挙動になるよう`settings-screen.tsx`の各操作ハンドラへ共通処理`handleUnauthorized`を追加した。TC-023は代表として表示名保存時の401を確認する（他の操作も同じ共通処理を通るため、個別のテストケースは設けていない）。
- 画面表示時（初回読み込み）の401は、`loadSettings`自体には`error.status === 401`を見るトースト付きの分岐があるものの、実際にはその手前の`fetchMe()`（`GET /auth/me`）が401を例外にせず`{ authenticated: false }`として返すため、`loadSettings`へ到達する前にトーストなしで即座にログイン画面へ遷移する。これはToDo一覧・ToDo詳細・家族グループ設定と同じ挙動であり、他画面と同じ判断（実装どおり）とした（TC-016）。`loadSettings`内の401分岐は、認証済みの状態でセッションが読み込みの合間だけ切れるごく狭い競合状態でのみ働く。
- 「通信できない」（設計書「7. エラー時の表示文言」の専用行）は、実装のいずれの操作ハンドラも通信エラーかどうかを判別せず常に操作別の汎用メッセージを表示するため、この画面ではどの操作でも実際には表示されない。TC-024は代表として表示名保存時の通信エラーを確認し、`表示名の保存に失敗しました。`（TC-017のサーバーエラー時と同じ文言）になることを実装どおりの仕様として記録する。
- Push通知の登録失敗時のメッセージは、当初「ブラウザで拒否された」場合と「購読情報の登録に失敗」した場合が実装上区別されておらず、後者も一律「通知が許可されませんでした。ブラウザの設定から許可できます。」と表示されていた。ユーザー承認のうえ設計書どおり、購読情報の登録に失敗した場合は`通知の設定に失敗しました。もう一度お試しください。`を表示するよう`handleRequestPushPermission`を修正した（TC-021・TC-022で区別して確認する）。
- 実際のPush購読登録（`PushManager.subscribe()`が実際のプッシュ配信サービスへの到達を要する）は、ToDo一覧のPush通知許可リクエストと同じくこのローカル検証環境のネットワーク到達性の制約により実施できないことがある。アプリの不具合ではないと判断し、その場合はテストコード側で`test.skip`により記録する（TC-007）。
- ログアウト（`POST /auth/logout`）のフロント側実装（`apps/frontend/src/modules/auth/api-client.ts`の`logout`）は応答のHTTPステータスを確認せず、常にログイン画面へ遷移する。そのため操作中の401をこの操作だけ個別に判定する意味が無く（401であっても最終的にログイン画面へ遷移する点は変わらないため）、`handleUnauthorized`の適用対象から除外している。
