# 単体テスト仕様書: ログイン

## 1. テスト対象
- 対象機能: ログイン（Google OAuth）
- 対象画面またはAPI: ログイン画面（`/`）、Googleコールバック画面（`/auth/callback`）
- 対象ファイル: `apps/frontend/src/modules/auth/ui/login-screen.tsx`、`apps/frontend/src/modules/auth/ui/oauth-callback-screen.tsx`、`apps/frontend/src/modules/auth/service.ts`、`apps/frontend/src/modules/auth/api-client.ts`
- 関連DBテーブル: `users`、`sessions`、`notification_settings`
- 関連設計書: [`10_ログイン.md`](../../../../specs/02_basic-design/family-todo/10_ログイン.md)

## 2. 前提条件
- 実行環境: ローカル（`pnpm dev:backend` = http://localhost:8787 / `pnpm dev:frontend` = http://localhost:3000）
- ログインユーザー: 実際のGoogleアカウントによる認可コードフローは検証環境にクレデンシャルが無く使用しない。[`ローカルD1へのセッション投入によるUI確認.md`](../../../../todo/notes/ローカルD1へのセッション投入によるUI確認.md)の手順で、テスト用ユーザーとセッションをD1へ直接投入し、ログイン済み状態を再現する
- 権限: 無し（設計書「6. 権限による差」のとおり、未ログインユーザー全員に同じ画面を表示する）
- 事前DB状態:
  - TC-005（未所属ユーザーの自動振り分け）用に、`family_id`が未設定のユーザー1名とその有効な`sessions`行
  - TC-006（所属済みユーザーの自動振り分け）用に、`family_id`が設定されたユーザー1名とその有効な`sessions`行
- 使用するテストデータ: 上記2ユーザー（`google_sub`はテスト用の任意値。例: `e2e-login-no-family` / `e2e-login-has-family`）

## 3. テスト観点
- 正常系: 初期表示、ボタン押下時のGoogle遷移URLの組み立て、ログイン済み状態からの自動振り分け、招待コードの引き継ぎ
- 異常系: コールバック画面からのエラー伝達、`GET /auth/me`のサーバーエラー・通信エラー
- 境界値: 該当なし（入力欄が無いため。「7. 補足」に記載し省略する）
- 権限: 該当なし（差が無いため。「7. 補足」に記載し省略する）
- DB更新: この画面自体はDBを更新しない（テスト用ユーザー・セッションの投入は準備作業であり、画面操作の結果ではない）
- 画面表示: `checking`→`ready`のローディング表示切り替え、ボタンの活性/非活性制御

- この画面では初回ログイン時に`users`・`notification_settings`への追加が発生するが（設計書「8. DBへの影響」）、それは`POST /auth/google/callback`成功後の実装（Backend側）の挙動であり、クレデンシャルが無く自動化できない。本仕様書のテストケースはいずれもBackend側のログイン処理を経由しない（Frontendの表示・遷移のみを検証する）ため、DB変化は無い。

## 6. 未確定事項
- 実際のGoogle認可コードフロー完走（ボタン押下→Google側の同意画面→コールバック成功）は検証環境にクレデンシャルが無く未検証。TC-002で遷移先URLの組み立てまでを確認し、ログイン成功後の振り分け（TC-005/TC-006）はローカルD1へのセッション直接投入で代替する（ユーザー承認済み）。

## 7. 補足
- 「境界値」「権限」の観点は対象外（入力欄が無く、権限による差も無い画面のため）。
- TC-003・TC-004で確認する`sessionStorage`の値は、Playwright側で`page.evaluate`等を用いて読み取る想定。
