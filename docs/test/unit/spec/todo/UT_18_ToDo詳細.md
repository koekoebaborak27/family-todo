# 単体テスト仕様書: ToDo詳細

## 1. テスト対象

- 対象機能: ToDo詳細
- 対象画面またはAPI: ToDo詳細画面（`/todos/:id`）
- 対象ファイル: `apps/frontend/src/modules/todo/ui/todo-detail-screen.tsx`、`apps/frontend/src/modules/todo/service.ts`、`apps/frontend/src/modules/todo/api-client.ts`、`apps/backend/src/modules/todo/routes.ts`、`apps/backend/src/modules/todo/service.ts`、`apps/backend/src/modules/todo/recurrence.ts`、`apps/backend/src/modules/todo/validation.ts`
- 関連DBテーブル: `families`、`users`、`categories`、`todos`、`todo_assignees`、`unregistered_members`、`comments`、`sessions`
- 関連設計書: [`18_ToDo詳細.md`](../../../../specs/02_basic-design/family-todo/18_ToDo詳細.md)、[`16_ToDo追加・編集.md`](../../../../specs/02_basic-design/family-todo/16_ToDo追加・編集.md)「8. DBへの影響 > 繰り返しToDoを完了にしたときの動き」、[`10_繰り返しToDoの期限計算.md`](../../../../specs/03_detail-design/family-todo/10_繰り返しToDoの期限計算.md)（本テスト仕様書作成にあわせて、設計書と実装の食い違い3点を解消・記載している。詳細は「7. 補足」参照）

## 2. 前提条件

- 実行環境: ローカル（`pnpm dev:backend` = http://localhost:8787 / `pnpm dev:frontend` = http://localhost:3000）
- ログインユーザー: 実際のGoogleアカウントは使用せず、[`ローカルD1へのセッション投入によるUI確認.md`](../../../../todo/notes/ローカルD1へのセッション投入によるUI確認.md)の手順でログイン済み状態を再現する
- 権限: 無し（設計書「6. 権限による差」のとおり、グループのメンバーであれば誰が作ったToDo・誰が書いたコメントでも操作できる）
- 事前DB状態（共通シード。以下の記号を各テストケースの「前提条件」列で参照する）:
  - `F1`: `families`に1件（`name = 'テスト家族'`）
  - `U1`: `users`に1件、`family_id = F1`、有効な`sessions`を持つ（ログイン中のユーザー本人。表示名「テスト太郎」）
  - `U2`: `users`に1件、`family_id = F1`（表示名「花子」）
  - `M1`: `unregistered_members`に1件、`family_id = F1`、`name = 'じいじ'`（非登録メンバー）
  - `categories`: 固定6件（学校・仕事・習い事・家事・買い物・その他）は既存のseedをそのまま使う
  - `T1`: `todos`に1件、`family_id = F1`、`title = '牛乳を買う'`、`status = incomplete`、`recurrence_type = none`、担当者は`U1`のみ。詳細確認・完了/未完了切り替え・削除の対象
  - `T2`: `todos`に1件、`family_id = F1`、`title = 'ゴミ出し'`、`status = incomplete`、`recurrence_type = daily`、`due_at`は今日のJST 00:00相当（UTC換算値）、`due_has_time = false`。繰り返しToDoの完了操作の対象
  - `T3`: `todos`に1件、`family_id = F1`、`due_at`が過去日時、`status = incomplete`（期限超過の表示確認用）
  - `C1`: `comments`に1件、`todo_id = T1のid`、`user_id = U2のid`、`body = '確認しました'`（投稿と更新日時が同じ＝未編集の状態）
  - 使用するテストデータ: 上記`F1`/`U1`/`U2`/`M1`/`categories`/`T1`/`T2`/`T3`/`C1`

## 3. テスト観点

- 正常系: 各表示項目（完了状態・タイトル・優先度・カテゴリ・期限・繰り返し・担当者・詳細メモ・作成者情報）の表示、完了/未完了の切り替え（繰り返しなし・あり）、編集・削除への遷移、コメントの投稿・編集・削除
- 異常系: ToDoが存在しない・他グループ（404）、不正なID、未認証（401）、グループ未所属（403）、完了/未完了切り替え失敗、削除失敗・削除対象なし、コメント操作の失敗・削除対象なし
- 境界値: コメント未入力（送信ボタン非活性）、コメント500文字ちょうど、コメント501文字（超過）
- 権限: 該当なし（「6. 権限による差」のとおり差が無いため。「7. 補足」に記載し省略する）
- DB更新: 完了/未完了の`status`・`completed_by_user_id`・`completed_at`の更新、繰り返しToDo完了時の`due_at`更新（`status`等は不変）、ToDo削除時の`todos`・`todo_assignees`・`comments`の物理削除、コメントの追加・更新・削除
- 画面表示: 完了状態バッジ・期限切れバッジ、担当者の「(未登録)」「(通知の受け取り役)」表記、コメント0件時のメッセージ、コメント送信ボタンの活性/非活性、削除確認ダイアログ
- エビデンス取得: 各操作後のスクリーンショット、DB確認が必要なケースはCSV/JSON出力

## 7. 補足

- 権限による差は無い（設計書「6. 権限による差」のとおり）ため、権限観点のテストケースは設けていない。
- 設計書「3.1」の完了者・完了日時の表示は当初「時刻を含めない」実装（ToDo一覧のカードと共通の`formatCompletedInfo`関数）になっていたが、設計書の例（`太郎 が 9/1(月) 20:15 に完了`）どおり時刻を表示する仕様であることをユーザーに確認し、ToDo詳細専用の`formatCompletedInfoWithTime`関数を実装した（`apps/frontend/src/modules/todo/service.ts`）。ToDo一覧のカード表示は既存どおり時刻なしのままで変更していない。
- 設計書「5. 操作と遷移先」「8. DBへの影響」の「繰り返しToDoを完了にしたときの動き」（次回の期限へ進める処理）は、当初バックエンドに実装が無く、繰り返し設定の有無にかかわらず常に完了として記録される状態だった。設計書どおりの挙動をユーザーに確認のうえ、[`10_繰り返しToDoの期限計算.md`](../../../../specs/03_detail-design/family-todo/10_繰り返しToDoの期限計算.md)に沿って`apps/backend/src/modules/todo/recurrence.ts`（次回の期限計算）と`completeTodo`（`apps/backend/src/modules/todo/service.ts`）を実装した。あわせて`POST /todos/:id/complete`の応答を`204`から`{ recurring: boolean; nextDueAt: string | null }`を返す`200`へ変更し、フロント（ToDo詳細・ToDo一覧の両画面）のトースト表示を対応させた。次回期限の計算アルゴリズム自体（毎日・毎週・毎月の境界値）はVitest（`apps/backend/src/modules/todo/recurrence.test.ts`）で担保しており、本仕様書のTC-011は画面からの一連の操作が実際に反映されることの確認に絞っている。
- コメントの投稿・編集・削除における401（セッション失効）・通信エラー時の挙動は、設計書が専用メッセージとログイン画面への遷移を求めていたのに対し、実装（`todo-detail-screen.tsx`の`handleCreateComment`/`handleUpdateComment`/`handleDeleteComment`）は404（対象が既に無い）以外のすべての失敗を一律の文言（`コメントの保存に失敗しました。`等）でトースト表示するのみだった。ユーザー承認のうえ、実装どおりの挙動をテスト対象とし、設計書「7. エラー時の表示文言」に注記を追加している。
