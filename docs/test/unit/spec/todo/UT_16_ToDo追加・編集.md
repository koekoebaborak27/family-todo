# 単体テスト仕様書: ToDo追加・編集

## 1. テスト対象
- 対象機能: ToDo追加・編集
- 対象画面またはAPI: ToDo追加・編集画面（新規作成 `/todos/new`、編集 `/todos/:id/edit`）
- 対象ファイル: `apps/frontend/src/modules/todo/ui/todo-form-screen.tsx`、`apps/frontend/src/modules/todo/api-client.ts`、`apps/backend/src/modules/todo/validation.ts`、`apps/backend/src/modules/todo/service.ts`
- 関連DBテーブル: `families`、`users`、`categories`、`todos`、`todo_assignees`、`unregistered_members`、`sessions`
- 関連設計書: [`16_ToDo追加・編集.md`](../../../../specs/02_basic-design/family-todo/16_ToDo追加・編集.md)（本テスト仕様書作成にあわせて、設計書と実装の食い違い2点の記載を、実装に合わせてテスト対象から除外・修正している。詳細は「7. 補足」参照）

## 2. 前提条件
- 実行環境: ローカル（`pnpm dev:backend` = http://localhost:8787 / `pnpm dev:frontend` = http://localhost:3000）
- ログインユーザー: 実際のGoogleアカウントは使用せず、[`ローカルD1へのセッション投入によるUI確認.md`](../../../../todo/notes/ローカルD1へのセッション投入によるUI確認.md)の手順でログイン済み状態を再現する
- 権限: 無し（設計書「6. 権限による差」のとおり、グループのメンバーであれば誰が作ったToDoでも編集できる）
- 事前DB状態（共通シード。以下の記号を各テストケースの「前提条件」列で参照する）:
  - `F1`: `families`に1件（`name = 'テスト家族'`）
  - `U1`: `users`に1件、`family_id = F1`、有効な`sessions`を持つ（ログイン中のユーザー本人。表示名「テスト太郎」）
  - `U2`: `users`に1件、`family_id = F1`（担当者用の別メンバー。表示名「花子」）
  - `M1`: `unregistered_members`に1件、`family_id = F1`、`name = 'じいじ'`（非登録メンバー）。非登録メンバーが0件の状態を確認するケースでは投入しない
  - `categories`: 固定6件（学校・仕事・習い事・家事・買い物・その他）は既存のseedをそのまま使う
  - `T1`: `todos`に1件、`family_id = F1`、編集対象。担当者は`U1`のみ（編集系テストケースで使用）
- 使用するテストデータ: 上記`F1`/`U1`/`U2`/`M1`/`categories`/`T1`

## 3. テスト観点
- 正常系: 新規作成の初期表示・保存、編集の初期表示・保存、担当者/非登録メンバー/フォロー役の選択、繰り返し（毎日・毎週・毎月）の保存、キャンセル
- 異常系: セッション失効（401）、グループ未所属（403）、編集対象が削除済み（404）、入力エラー（400）、サーバーエラー・通信エラー
- 境界値: タイトル100文字ちょうど／101文字、詳細メモ1000文字ちょうど／1001文字、未入力必須項目（タイトル・カテゴリ・優先度・期限日付・期限時刻・繰り返し曜日・繰り返し日付・フォロー役）
- 権限: 該当なし（「6. 権限による差」のとおり差が無いため。「7. 補足」に記載し省略する）
- DB更新: 新規作成時の`todos`・`todo_assignees`追加、編集時の`todos`更新・`todo_assignees`総入れ替え、繰り返し種別ごとの`recurrence_type`/`recurrence_config`の保存形式
- 画面表示: 新規/編集でのタイトル・保存ボタン文言切り替え、期限のON/OFFによる日付・時刻欄の表示制御、繰り返し種別による追加欄の表示制御、非登録メンバー選択によるフォロー役欄の表示制御、非登録メンバー0件時のメッセージ、送信中のボタン操作不可

## 7. 補足
- 設計書「5. 操作と遷移先」に「キャンセルまたは戻るを押す。入力に変更がある場合は確認ダイアログ（`AlertDialog`）で『入力中の内容は保存されません。編集をやめますか？』を表示し、承諾したら破棄する。」とあるが、実装（`todo-form-screen.tsx`の「キャンセル」ボタン）は`router.back()`を直接呼ぶのみで、変更の有無にかかわらず確認ダイアログを表示しない。ユーザー承認のうえ、本仕様書ではTC-019を実装どおり（確認ダイアログなし）の内容としている。
- 設計書「7. エラー時の表示文言」は「該当項目があれば項目の下に表示し、エラーがある項目のうち一番上のものへ画面を送る」としているが、実装は入力チェック・サーバーからの400応答のいずれも画面上部の単一のエラー表示（`role="alert"`のp要素）にまとめて表示するのみで、項目ごとの個別表示や自動スクロールは行わない。ユーザー承認のうえ、本仕様書のTC-020・TC-021・TC-023・TC-025〜TC-029は実装どおり（画面上部への表示）の内容としている。
- 「フォロー役が不足（400）」はサーバー側でも`ensureAssigneesInMyFamily`とは別に`replaceAssigneesSchema`のバリデーションで弾かれるが、通常の画面操作では送信前にクライアント側バリデーション（TC-029）で止まるため、サーバー側400を発生させる専用のテストケースは設けていない。
- 「繰り返しToDoを完了にしたときの動き」（設計書「8. DBへの影響」の該当節）は完了操作そのものがToDo一覧・ToDo詳細画面側の機能であり、本画面（追加・編集）の操作範囲外のためテスト対象外とする。
